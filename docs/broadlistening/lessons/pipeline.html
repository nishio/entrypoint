Analysis Pipeline

Translated from the Japanese original: wiki/concepts/pipeline.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: Analysis pipeline — extraction → embedding → hierarchical clustering → labeling → visualization

Placement (Important: canonical location has been moved)

The canonical implementation as of 2026 is packages/analysis-core/src/analysis_core/steps/. All 8 steps are here.

After the legacy cleanup merge on 2026-05-23, the old Python implementation no longer remains in apps/api/broadlistening/pipeline/. What remains in the current tree are only sample configs/ / inputs/, and the canonical path for the execution code has been unified into analysis-core. For details, see refactoring-status.

  • Entry point (recommended): python -m analysis_core or kouchou-analyze (cli)

Step Sequence

  1. extraction — Extract "opinions" from raw comments using LLMs (highest cost)
  2. embedding — Convert each opinion into an embedding vector
  3. hierarchical_clustering — Hierarchical clustering (first layer / second layer)
  4. hierarchical_initial_labelling — Initial labels for each cluster
  5. hierarchical_merge_labelling — Upper-level label integration
  6. hierarchical_overview — Overall summary
  7. hierarchical_aggregation — Generate aggregated report
  8. hierarchical_visualization — Output scatter plot, treemap, dense-scatter

Execution Modes

There are **2 lineages** in analysis_core.PipelineOrchestrator:

  • run_default() / run_workflow() — The current canonical path. The CLI and API server use this.
  • run() — A direct-step fallback. It remains for compatibility but is deprecated, and is not the canonical path (refactoring-status).

From a user's perspective, this corresponds to the core of the **CLI mode** in usage-modes. Even in the Web UI mode, the calculation itself shares this pipeline, but the display routing diverges on the public-viewer side.

How the LLM grouping-based LLM classification was expected to be inserted

In the week of 2026-02-11 in slack-dev-kouchouai-2026-q1, a **branch that diverges to LLM-based clustering after extraction, embedding** is mentioned as an idea for the near future. This is not the theoretically optimal form, but a compatibility-first proposal to **verify the analysis switching part while maintaining compatibility with the existing pipeline and visualization** first.

In the week of 2026-02-25 of the same source, it is also organized that branching after embedding is for "ease of implementation" and "later visualization," and that embedding is not logically essential.
In short, **the near-term branch uses embedding as a stepping stone, but in the long term, there is room to move the classification criteria itself from the metric space to a classification tree**.

Location and Schema of Outputs

Under {output_base_dir}/{report_id}/ (specified by --output-dir in the CLI. For the API server, settings.REPORT_DIR):

  • args.csv — List of extracted opinions (kebab-case columns: arg-id, comment-id, etc.)
  • embeddings.pkl — **The original embedding vectors** (not 2D after UMAP)
  • hierarchical_clusters.csv — Cluster hierarchy
  • hierarchical_result.json — The integrated result read by the viewer
  • final_result_with_comments.csv — Output when config.is_pubcom=true. **Only this CSV is snake_case** (arg_id, category_id) — others are kebab-case (gotchas)

Detailed schema is in docs/development/plugin-output-data-structures.md.

Major Hidden Assumptions and Pitfalls

  • **There are traces on Slack that embeddings.pkl was mistakenly recognized as 2D after UMAP** (slack-dev-kouchouai-2025-q4), but in the code of main@3809a7a, the embedding step saves the original embedding vectors into embeddings.pkl, and the hierarchical_clustering step reads it before reducing it to 2D with UMAP (source-code)
  • **The automatic numbering of comment-id is path-dependent**: Web CSV uploads and spreadsheet imports automatically generate it, but for CLI/plugins/direct CSV, the plugin side is responsible for issuing the comment-id
  • **propertyMap** (hierarchical_result.json): hierarchical_aggregation crashes if there is no corresponding column in args.csv
  • **Case inconsistency of CSV column names**: Only the is_pubcom=true path is snake_case
  • **E2E pipeline tests are billed**: About $0.01/run with gpt-4o-mini. Excluded from the default pytest by norecursedirs = ["tests/e2e"] in pyproject.toml, and not executed in CI either

The Default Issue with Cluster Numbers

Resurfaced under the meeting-minutes 2026-05-18 heading: The example in docs/user-guide/cli-quickstart.md is [3, 6]. Claude Code uses this exactly as is, resulting in a coarse grouping like 3 → 6 → 12 → 24 even for datasets of around 300 items.
In Issue #830 / PR #832 on 2026-05-18, the direction to make cluster_nums optional and automatically calculate it from the number of arguments after extraction using the cube-root rule when unspecified materialized, and was subsequently merged. For argument_count=1000, it returns [10, 100], and the small dataset side is also patched to 2 -> [2], 3 -> [2, 3]. From issue-830-pr-832-auto-cluster-defaults-2026-05-18.

In the past, kitaro also implemented an automatic selection based on silhouette-score in PR #567, but it was reverted in #579 due to triggering embedding errors. The current change is not a retry of that, but rather is more accurately understood as a **modification to align CLI / analysis-core with the simple recommended value rules already present on the Admin side**. From issue-830-pr-832-auto-cluster-defaults-2026-05-18.

Why UMAP → Clustering? (Known Theoretical Weaknesses)

meeting-minutes 2025-10-08: Research-wise, it is known that directly applying HDBSCAN in high dimensions yields higher accuracy, but since humans cannot see high dimensions, the current configuration is maintained as a trade-off with the readability of scatter plots. If one wants to try an alternative, the policy is to implement it as an analysis plugin.

Additionally, in slack-kouchouai-algorithm-dev, from 2025-05 to 2026-03, there have been ongoing criticisms:

  • It is easy to read meaning into UMAP axes
  • Accuracy drops when performing k-means after reducing to 2D
  • Pros and cons within the same topic are easily placed close together

Therefore, the current configuration should be read not as something "believed to be theoretically sound," but rather as a **provisional form prioritizing visualization convenience**.

Book section 13.2.4 (broad-listening-book-source) similarly clarifies that the UMAP → clustering order is "a choice different from the standard practice in machine learning, and involves design compromises." This serves as a source for quotation when explaining it externally as a finalized design decision in a publishable form. Section 13.5 organizes a two-architecture comparison between the **scatter plot type vs. Long Context type** prompted by the expansion of LLM context windows, which aligns with the analysis_mode strategy of pr-827-llm-grouping-capabilities-plan-2026-05-18. For details, see broad-listening-book-extractions.

Lightweighting and CLI Static Output (2026-05)

meeting-minutes 2026-05-18 heading / PR #825:

  • Previously, it was necessary to "set up a server and npm run build," but AI coding agents want to "output HTML without a server and statically host it"
  • Added implementation to output static HTML directly from Python. The policy is to make this the default
  • The appearance is not 100% identical to the old server path — there is a byproduct of being "easy to try experimental views"
  • However, the main path of the current product is still to render hierarchical_result.json with the public-viewer, and it is more accurate to understand report.html as an observation HTML for the CLI

What PR #827 materialized

In pr-827-llm-grouping-capabilities-plan-2026-05-18, the **"compatible branch to insert LLM classification after embedding"** envisioned on Slack is verbalized as a more concrete transition plan.

  • In the short term, add analysis_mode=llm_grouping while leaving embedding, and maintain viewer compatibility by outputting x/y and cluster-level-* in the conventional format
  • In the long term, automatically derive analysis_capabilities from actual data, and judge the availability of visualization modes with requirements

This is consistent with the intention of slack-dev-kouchouai-2026-q1 to "first try analysis switching in a way that is compatible with the existing pipeline and visualization." On the other hand, when considering this second mode specifically as one for **LLM direct grouping**, it also becomes apparent that the short-term compatibility plan itself is nothing more than a "provisional measure of projecting temporarily into a scatter-compatible form." The original output of the LLM grouping lineage is tree / taxonomy / stance grouping, and it is highly likely that a scatter plot is not a natural primary artifact. Therefore, the core objective in the long term is not to increase the number of modes, but to **create a capability contract where the product is viable even in an analysis mode that does not assume a scatter plot**. It is reasonable to view that the production implementation for that was uninitiated in main as of 2026-05-18.
