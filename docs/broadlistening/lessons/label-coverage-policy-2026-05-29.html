Labels are Summaries, not Tables of Contents — Human Judgment in Label Design

Translated from the Japanese original: wiki/analyses/label-coverage-policy-2026-05-29.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: Human judgment on label design: Labels should be organized as "summaries" rather than "tables of contents," covering up to the top 2-3 axes. However, the evaluation criteria depend on the use case, and the desirable behavior of sampling, rep args, and judge changes between grasping the overall trend and discovering a small number of important issues. One of the root causes for dimensions dropping out of labels is that the upstream labeling input is a random sampling of up to 30 items via API and 10 items in CLI/default.

In response to the results where Claude judge raised 3 issues "to be assigned to humans" in label-refinement-input-scope-2026-05-29, human judgments were returned from multiple people in the Slack discussion from 2026-05-29 to 30. At the same time, tokoroten pointed out the upstream sampling constraints, ohki-shingo pointed out that the evaluation axes change depending on the use case, and code verification revealed that the "root cause of axes dropping out of labels" exists even before refinement. This page organizes those judgments and policies in the product context. From label-refinement-judge-bundle-2026-05-25, from slack-label-algorithm-improvement-2026-05-30

Issue 1: "Short but missing" vs. "Long but redundant"

Human judgment: Prioritize coverage, tolerate redundancy.

A writing style like AIによる持続可能な社会構築 in balanced where the 災害対応 axis drops out makes it easier to scan, but for users it looks like "topics outside the label are mixed in the cluster". In tokoroten's words, "it feels worse when things outside the category are included." Therefore, even if it is long like the none series, it is on the safer side if all dimensions appear in the label. From label-refinement-judge-bundle-2026-05-25

This is a product definition choice to treat labels not as "table of contents headings on the list UI" but as "cluster summaries".

Issue 2: Up to how many missing items are OK?

Human judgment: Complete coverage with 1 keyword is impossible. Compromise in the direction of expanding to the extent of "A and B" with the top 2-3 keywords.

It is rare that all 26 items in a cluster can be expressed with 1 keyword A, and it is impossible to "throw away absolutely nothing". However, we want to minimize the loss. The specific idea is as follows:

  • First, take the most frequent topic A
  • Take the next most frequent B among the residuals not covered by A
  • Make the label in the format A and B
  • Do not allow 4 or more axes like A and B and C and D (scanability breaks down)

This is the idea of greedy max-coverage, and it also leads to the discussion of shifting the way of taking upstream sampling and rep args to "maximum coverage".

Proposed Algorithm Candidates

Plan Overview Cost
tokoroten plan Choose the title that maximizes the sum of cos similarities between the title candidate embedding and each element embedding ∑ cos(emb(title), emb(item)) Light with only embedding calculation
nishio plan 1 Generate multiple title candidates with LLM → score by emb distance → select LLM calls increase for the generated candidates
nishio plan 2 Directly score whether each data point is covered by the title and choose the best candidate Assuming cost is disregarded
nishio plan 3 Show multiple candidates on the UI and let humans choose Calculation cost is medium, valuable as a UX that takes over the burden of verbalizing user preferences

None of these are things to be put into the main pipeline immediately, but are worth comparing as an experimental step.

Issue 3: Colloquial register like "entertainment"

Human judgment: Depends on the use case. At worst, it can be absorbed by string replacement.

The issue of colloquialisms being mixed in, like AIによるエンタメと研究革新 in contrast, has a tolerance that changes depending on the tone of the product (assistance for policy decision-making vs. lightweight report). The priority is lower than issues 1 and 2, and they can be aligned with post-processing if necessary.

Premise: Output for which use case?

In the Slack on 2026-05-30, ohki-shingo pointed out that the direction to tackle changes depending on specifically which use case's output we want to improve. For example, whether we want to grasp the overall trend or discover a small number of seemingly important issues, the appropriate processing and evaluation are different. From slack-label-algorithm-improvement-2026-05-30

This is not a story that weakens the above "omission NG" policy, but a correction that we need to define what is called an omission first.

  • Grasping the overall trend: Labels should stably summarize the top topics with large cluster mass. Accidental omissions due to random sampling should be avoided, but stuffing even minuscule edge cases into the label will ruin scanability.
  • Discovering a small number of important issues: It is unreasonable to stuff all minority dimensions into the label alone. Rather, it is better to pick them up with a separate artifact like examples showing breadth, boundary examples, minority flag, or subtopic list.
  • Accountability of public UI: The label is an entrance, and it is necessary to avoid misguidance as a set with description / rep args / drill-down to individual opinions.

Therefore, in the next experiment, it is necessary to specify not only whether the label quality improves with full-item input, but also which use case's quality is being measured in the run metadata and judge prompt.

Upstream Sampling Constraints (New Discovery)

While discussing Issue 2, tokoroten pointed out the possibility that "some specimens may not be read, causing information to drop out from the label" during sampling for labeling. Checking the actual code shows the following.

  • packages/analysis-core/src/analysis_core/steps/hierarchical_initial_labelling.py:154-155
  • packages/analysis-core/src/analysis_core/steps/hierarchical_merge_labelling.py:262-266

Both cut the number of items with sampling_num = min(sampling_num, len(cluster_data)) and then call cluster_data.sample(n=sampling_num). This is DataFrame.sample in polars and is complete random sampling.

The maximum number of items differs depending on the execution path:

  • Normal report creation via admin screen/API: apps/api/src/services/report_launcher.py:42-49 specifies sampling_num = 30 for both initial / merge
  • analysis-core CLI / config default / builtin plugin default: sampling_num = 10 for both initial / merge
  • compat/config_converter.py:120 / 129: setdefault("sampling_num", 10) (both initial / merge)
  • plugins/builtin/hierarchical_initial_labelling.py:51: step_config.get("sampling_num", 10)
  • plugins/builtin/hierarchical_merge_labelling.py:51: step_config.get("sampling_num", 10)

In other words, in the normal Web path, if a cluster has more than 30 opinions, the labeling targets are randomly selected 30 items, and in the CLI/default path, if there are more than 10 items, only randomly selected 10 items are chosen. tokoroten's statement of "default 30" is correct via the API, and looking only at the analysis-core default, it is 10. The essence that "information drops out due to random sampling" is the same for both paths. From source-code

What this means for Issues 1 and 2:

  • The larger the cluster, the more the dimensions reflected in the label are pulled by the randomly hit 10/30 items rather than the "entity of the cluster".
  • Even if it is rewritten by refinement, the upstream random bias cannot be recovered (since refinement does not see rep args label-refinement-input-scope-2026-05-29).
  • To realize coverage-oriented labels, rather than increasing the input for refinement, it is more essential to switch the sampling strategy of hierarchical_initial_labelling to random → farthest point sampling / max coverage / k-medoids.

The same problem also applies to rep args display on the UI

Separately from the sampling during labeling, when displaying "label + 3-5 rep args" on the UI, which args to choose (random vs. highly representative ones covered by the label) is also a series of the same maximum coverage problem.

In the current main 0c294da, the normal overview (ClusterOverview) of the public-viewer has only the label / count / takeaway, and representative arguments are not lined up. In the hierarchical list display (HierarchyListChart), arguments can be expanded only for the deepest-level cluster, but representative selection is not done here either. The implementation picks up the arguments of the target cluster with argumentList.filter((arg) => arg.cluster_ids.includes(cluster.id)), and the initial display is argumentsList.slice(0, 10). In other words, it is the first 10 items of the array, and neither maximum coverage, label fitness, cluster centrality, nor random redrawing. Since the aggregation packs all items of the arguments array of hierarchical_result.json in the row order of hierarchical_clusters.csv, the display order largely follows the upstream argument order. From source-code

When putting in representative example selection, things near the cluster center or things with high similarity to the label embedding give a sense of conviction, but just that will make the scattering within the cluster look underestimated. If only typical examples are lined up, even a cluster that actually includes multiple axes and peripheral issues will easily look like a "single issue beautifully gathered at the center", inviting overconfidence in both the public UI and judge input.

Therefore, it is better for rep args not to be 1 type of "representative", but to divide at least the following.

  • Typical example: An argument near the centroid, or with high similarity to the label embedding. Used to quickly understand the meaning of the label.
  • Example showing breadth: An argument that is far from the typical example but belongs to the cluster, or an argument chosen by FPS / k-medoids / subtopic coverage. Used to show the scattering and sub-issues that the cluster holds.
  • Boundary example: An argument near the boundary with a sibling cluster. Used to inspect places where the difference between labels is ambiguous.

On the UI, rather than just "3 representative examples", taking them out by dividing roles like typical example 2 + breadth 2 + boundary 1 makes it easier to balance conviction and underrepresentation. It is the same for judge input; passing only typical examples easily leads to overestimating the goodness of the label.

Lessons from Experimental Operations

The flow this time:

  1. Felt that GPT judge was untrustworthy.
  2. Spit out the target of judgment into Markdown in a fixed format (label-refinement-judge-bundle-2026-05-25).
  3. Let Claude Code judge it.
  4. Asked Claude, "Are there things that should be confirmed with humans?", and drew out 3 issues.
  5. Gathered human judgments on Slack, and even a hypothesis on upstream sampling came out from tokoroten.
  6. Confirmed the hypothesis with code, and fixed it as a policy on this page.

This loop functioned as a division of labor: "Codex executes the experiment → Claude judges and cuts the issues → Humans decide the policy". This same format can be used when running experiments on sampling strategies and title selection algorithms in the future.

Open Questions

  • What is the implementation cost of switching the sampling of hierarchical_initial_labelling to max coverage / FPS? Should merge_labelling also be switched in the same way?
  • When implementing the tokoroten plan that chooses label candidates by the sum of embedding similarities, how many candidates is it practical to generate? (trade-off with the number of LLM calls)
  • When dividing the rep args passed to UI / judge into typical example / example showing breadth / boundary example, how many of each is it good to put out? Is a small composition like typical example 2 + breadth 2 + boundary 1 sufficient for now?
  • Where is the place to clearly write the coverage policy of "up to the top 2-3 axes" as a product? (refinement prompt? UI specifications? guidelines?)
  • In what phase should the UX that lets humans choose candidates on the UI (Plan 3) be positioned? (admin UX at the time of creation? review UX after publication?)
  • If grasping the overall trend and discovering a small number of important issues are treated as separate modes, which parts of label / description / rep args / judge rubric should be made common, and which should be separated?

  • 2026-05-29: Point from nishio: "Since it is already known that the cost of the labeling part is very small compared to extraction, wouldn't a simple experiment of first passing all items to try, and reducing them if that doesn't work be sufficient before jumping to complex algorithms like max coverage / FPS?". This is valid, and the policy written in the first edition to "switch the sampling strategy to random → max coverage / FPS / k-medoids" was premature. The order is reorganized as follows:
    1. First experiment: Effectively disable sampling_num (sufficiently large value or None) and pass all items to the labeling LLM to see if the label quality improves. Since the number of LLM calls does not change and only the token amount of each call increases, the cost increase compared to extraction is small.
    2. Only if the quality does not improve with (1), or if a cluster where the context window is realistically severe appears, proceed to the comparison of max coverage / FPS / k-medoids.
    3. The tokoroten plan (maximizing the sum of cos similarities of title candidate emb × each element emb) is an improvement on a different axis from "whether the LLM can write a label with representativeness from a long context" which remains even in (1), so it can be experimented in parallel.
    By using this order, it can be confirmed at the minimum cost whether "upstream sampling is really the bottleneck".
