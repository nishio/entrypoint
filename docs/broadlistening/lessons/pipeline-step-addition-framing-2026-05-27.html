Pipeline Step Addition Framing 2026-05-27

Translated from the Japanese original: wiki/analyses/pipeline-step-addition-framing-2026-05-27.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: The proposal to add pipeline steps, which repeatedly appeared in recent research, should be judged not by the number of steps but by whether 'new artifact responsibilities should be made first-class'. Boundary cases, counterexamples, and bridges should be independent artifacts, while mere label copy improvements should be kept as experimental optional steps.

In recent research memos, proposals for 'adding a step to the pipeline' have appeared multiple times. On the surface, it seems like a discussion about increasing the number of steps, but in reality, we should consider the following two lineages separately.

  1. Post-processing of the top-level label set, such as hierarchical_label_refinement. This is an experiment to adjust the brevity, granularity, and differences of headings after merge_labelling without changing the existing cluster structure. From llm-grouping-experiment-output-2026-05-25.
  2. Artifacts with interpretation and explanation responsibilities, such as representative_docs, boundary_cases, counterexamples, unresolved_cards, and bridge edge reason. This has repeatedly appeared in multiple places in UMAP / BERTopic related research, LLM pairwise graph, MST + bridge visualization, and KJ method (KJ法) brainstorming. From gpt-umap-clustering-bertopic-deep-research-2026-05-25, gpt-llm-pairwise-spectral-small-n-brainstorm-2026-05-25, gpt-mst-bridge-visualization-brainstorm-2026-05-25, gpt-kawakita-kj-method-broadlistening-2026-05-25.

Conclusion

The judgment criterion should be placed on whether 'responsibilities are increasing but hidden in existing steps', rather than 'whether the number of steps increases'.

  • For mere prompt variants, copy tuning, and shortening for UI headings, the concepts of the default pipeline should not be increased. Treat them as experimental optional steps or modes of existing labeling-related steps.
  • On the other hand, for artifacts used independently by subsequent reports / UI / audit / human reviews, such as boundary cases, counterexamples, bridges, unresolved cards, and rationale edges, cramming them into existing aggregation or visualization would make things more complex. These should be separated into steps / capabilities as first-class artifacts.

In other words, step additions should generally be avoided, but steps necessary for separating responsibilities should be added. Without this boundary, short-term 'simplicity' will turn into long-term incomprehensibility.

Looking from the High-Level Purpose

kouchou-ai (広聴AI) is an OSS implementation of broad listening that includes operations by municipalities, political parties, and non-engineers, centered on creating an 'opinion map' from free-text comments. From kouchou-ai and broadlistening.

However, recent KJ method brainstorming reinterprets the purpose of Kouchou-AI at an even higher level as 'a device to raise public hypotheses from chaos'. From gpt-kawakita-kj-method-broadlistening-2026-05-25.

In light of this purpose, simply 'putting all opinions into some cluster and attaching clean headings' is not enough. Rather, what is important is:

  • Being able to return to the original text
  • Not erasing minority opinions or opinions that are difficult to classify
  • Being able to show cluster boundaries, counterexamples, adjacent issues, causality, and opposition
  • Leaving rationales for humans to review the organization produced by AI

These are not of a nature that can be solved by simply adding a bit more text to aggregation. If they do not remain as artifacts, they cannot be reused in the UI or reviews, and cannot serve as a foothold for examination as public hypotheses.

Concerns on the 'Complexity Increases' Side

The concern about adding steps is valid. The current pipeline is already a multi-stage structure of extraction → embedding → clustering → labelling → overview → aggregation → visualization, involving status, rerun, config, spec, token usage, and error handling. From pipeline.

If steps are added indiscriminately to this, the following will happen.

  • Execution time and token cost increase
  • Tracking for status UI and spec increases
  • Combinations of skip / rerun increase
  • Artifact versioning increases
  • It becomes harder for users to understand 'what should be configured'

Particularly, label_refinement runs this risk. While this is useful as an experiment to improve the readability of the label list, it is not the fundamental purpose of the project itself. If prompt variations like setwise / contrast / balanced proliferate as steps, the pipeline will bloat with the history of prompt experiments. From llm-grouping-experiment-output-2026-05-25.

Therefore, for the time being, label_refinement should be treated as an experimental step that is default off / mode=none, and once stabilized, it would be best to absorb it into an internal mode of the 'semantic presentation' lineage. It is too early to strongly promote this as a permanent major stage of the product.

Concerns on the Side Where Cramming Makes it More Complex

On the other hand, cramming everything into existing steps is also dangerous.

For example, if aggregation is tasked with heading shortening, representative document selection, boundary case extraction, counterexample detection, bridge edge classification, KJ-like unresolved cards, and report text generation all at once, the surface number of steps will not increase. However, in reality, a single step will carry multiple different artifacts and failure modes.

The complexity in this case is worse.

  • It is unclear what one wants to rerun
  • It is unclear which prompt affected which artifact
  • Artifacts required by the UI and report text generation become tightly coupled
  • It becomes impossible to evaluate whether the 'cluster is bad' or the 'explanation artifact is bad'
  • Later, when creating a graph view or KJ view, one will end up having to re-extract information from the text

Recent research consistently moves in the direction of separating analysis artifacts, display artifacts, and explanation artifacts. The proposals to separate UMAP 2D and clustering spaces, to leave reasons in the LLM pairwise graph, to display relation types with MST + bridge, and to leave unresolved_cards.md in the KJ method all belong to this trend. From gpt-umap-clustering-bertopic-deep-research-2026-05-25, gpt-llm-pairwise-spectral-small-n-brainstorm-2026-05-25, gpt-mst-bridge-visualization-brainstorm-2026-05-25, gpt-kawakita-kj-method-broadlistening-2026-05-25.

Therefore, carving out boundary cases, counterexamples, bridges, and unresolved cards as interpretation artifacts rather than text generation tasks within aggregation is simpler in the long run.

Recommended Pipeline Shape

If aligned with current names, the following decomposition of responsibilities is good for the short to medium term.

extraction
  -> embedding / llm_pairwise_affinity
  -> structure
       hierarchical_clustering / llm_grouping / pairwise_spectral
  -> labelling
       initial_labelling / merge_labelling
  -> optional label_refinement
       experiments for UI heading / label set readability
  -> interpretation_artifacts
       representative_docs
       boundary_cases
       counterexamples
       unresolved_cards
       bridge_edges + relation_type + reason
  -> overview / aggregation
       report text and publishable summary
  -> visualization
       scatter / tree / graph / KJ board

What is important is to not necessarily make interpretation_artifacts the same way in all modes. In large-scale scatter systems, they can be output approximately from the vicinity of embeddings / clusters; in small-scale LLM pairwise systems, they can naturally be output from edge reasons; and in KJ systems, they can be output as board artifacts premised on human editing. What should be standardized is not the implementation but the artifact contract / capability. This aligns with the long-term strategy that we should create a contract where the product remains viable even in modes without a scatter plot. From strategic-development-order-2026-05-23.

Judgment Criteria

Conditions under which it is acceptable to create a new step:

  • Outputs an independent artifact that can be referenced from subsequent steps
  • Has two or more downstream consumers, or could have them in the future
  • When it fails, one wants to rerun and verify only that step
  • The evaluation metric differs from existing steps
  • The viewer / report can judge its availability as analysis_capabilities

Conditions under which it should remain a mode of an existing step:

  • The output artifact is the same, and only the expression changes
  • The main purpose is comparing prompt variants
  • It is close to adjusting UI copy
  • Even if it fails, the semantic structure of the pipeline as a whole does not change
  • It is a one-off experiment with no reuse contract

By these criteria, label_refinement leans towards being a mode / optional step, and interpretation_artifacts leans towards being a first-class step / capability.

Practical Judgment

The following policy is good for the time being.

  1. label_refinement may be kept, but should not be shown as default complexity. Its purpose should be limited to 'experiments on label set readability', and prompt variants should not be continually increased.
  2. Boundary cases, counterexamples, bridges, and unresolved cards should not be mixed into aggregation; their artifact schemas should be designed first. Initially, intermediate artifacts in CSV / JSON will suffice.
  3. Do not immediately expose them to the UI. First, save them as CLI / research outputs, and let humans read them to determine their value.
  4. Only load those whose value has been confirmed into analysis_capabilities, making them usable by graph views / KJ views / report sections.
  5. In the non-expert experience of the Web UI, do not show the number of steps. Even if internal workflows increase, present them to users in units of artifacts like 'whether to display rationales, boundaries, and unresolved cases'.

In other words, for the project, properly separating artifact responsibilities is more important than protecting the pipeline as a fixed box of 8 steps. However, that is different from adding prompt experiments as steps.

Corrections Based on 2026-05-28 Open PRs

Among the open PRs as of 2026-05-28 00:08 JST, three are directly related to yesterday's abstract discussion. From open-pr-pipeline-step-observation-2026-05-28.

#866 LLM grouping is a good example of avoiding cramming into existing steps

#866 adds analysis_mode=llm_grouping, the analysis.llm_grouping plugin, and a dedicated spec / workflow, and outputs existing viewer-compatible hierarchical_clusters.csv / hierarchical_merge_labels.csv. Even in the PR body, it is explicitly stated that this is an experimental entry point that maintains scatter plot compatibility, and that label refinement is not included as a separate issue. From open-pr-pipeline-step-observation-2026-05-28.

This is a design that isolates LLM grouping as a separate analysis_mode / workflow, rather than 'cramming LLM grouping into a mode of existing hierarchical_clustering'. While there is a limit to keeping embedding-derived x/y for short-term compatibility, it is appropriate as a PR that creates an experimental entry point while recognizing that limitation.

Judgment:

  • The direction may be maintained
  • Even after merging, do not evaluate 'the value of LLM grouping' based solely on scatter plot quality
  • Proceed in the next stage to analysis_capabilities and receptacles for non-scatter views

#867 reuse-from is a foundation for reducing the complexity of step additions

#867 allows seeding intermediate artifacts from existing outputs using --reuse-from and skipping corresponding steps. From open-pr-pipeline-step-observation-2026-05-28.

While this is not a new analysis method directly, it is important when adding downstream steps like label_refinement, layout_generation, and future interpretation_artifacts. Adding steps increases rerun costs and status complexity, but with reuse / skip, one can run experiments where 'extraction, embedding, and clustering are fixed and only the downstream is compared'.

Judgment:

  • This PR is of high value to be included prior to step additions themselves
  • If testing interpretation_artifacts, it is best to design experiments with --reuse-from as a premise

#874 semantic island layout is treated as a display artifact for experimental paths

#874 adds a hierarchical_layout_generation step between aggregation and visualization, and adds named layouts like embedding_umap / semantic_island_map to hierarchical_result.json.layouts. Existing arguments[].x/y are left as embedding-derived coordinates. From open-pr-pipeline-step-observation-2026-05-28.

This makes sense as an 'independent step of an experimental path'. This is because it is creating display artifacts that subsequent viewers can independently select, rather than mere prompt variants. Particularly, the design of making layouts a separate field without overwriting arguments[].x/y preserves both backward compatibility and the separation of responsibilities.

However, the reason to add it permanently to the standard pipeline is still weak. Because #874 constantly adds layout_generation to the default hierarchical workflow, the pipeline changes from an 8-step premise to a 9-step premise. Actually, in CI, in addition to Ruff's import / np annotation issues, Pytest is failing due to lingering fixed expectations of len(specs) == 8 / len(plan) == 8 / len(orchestrator.steps) == 8. From open-pr-pipeline-step-observation-2026-05-28.

This should be read not as a mere omission of a test fix, but as a gate to prevent experimental display functions from entering the standard pipeline. Therefore, #874 should be treated as an experimental path clarifying the following. From pipeline-step-default-policy-decision-2026-05-28.

  • layout_generation is not an analysis step but a display artifact step
  • Differentiate between the value of creating embedding_umap in all runs and the value of creating semantic_island_map restricted to llm_grouping
  • Decide whether layouts should be created even when without_html is true
  • Do not permanently include it in the standard workflow, and decide whether to explicitly enable it via capability, config, or analysis mode

Judgment:

  • Affirm the design direction of #874. Adding named layout artifacts without breaking x/y is correct
  • However, it is incorrect to add it to the standard pipeline. At this stage, return it to a form where it is explicitly enabled as an experimental route
  • #874 is not interpretation_artifacts. This is making 'display artifacts' first-class, and making boundary, counterexample, and bridge reasons first-class remains a separate issue

Merge / Review Order Based on Open PRs

Looking only at this issue, the following order is natural.

  1. #867 — green. It is the foundation for comparing downstream steps, so its priority is high.
  2. #866 — green. The direction of carving out a new mode as a workflow is appropriate.
  3. #874 — its design makes sense as an experiment, but it will not be permanently added to the standard workflow. Review it on the premise that it will be returned to an explicitly enabled experimental route after #866 / #867.

#863, #868, and #873 are each important, but will be treated in a separate lane from the decision to add pipeline steps.

The judgment on #874 has been carved out to pipeline-step-default-policy-decision-2026-05-28. The focus is not on 'can we increase steps' in general, but on whether there is a reason to permanently add experimental semantic island layout generation to the standard pipeline. At this point, that reason is weak, and the fixed 8 steps test will be maintained.

Open Questions

  • Should the schema for interpretation_artifacts be put into the existing hierarchical_result.json, or placed as a separate JSON?
  • How should unresolved_cards be reconciled with exhaustive partitioning? Rather than cluster_id = unresolved, it might be safer to have flags: ["boundary", "counterexample"] in addition to normal cluster assignments.
  • Will label_refinement be absorbed into merge_labelling in the future, or renamed to a broader step like semantic_presentation?
  • To what extent can boundaries / bridges be automatically extracted in large-scale data? We should not expect the same quality as with small-scale LLM pairwise.
  • What is the best unit to explicitly enable hierarchical_layout_generation in #874: config, analysis mode, or workflow variant?
  • To what extent should the fixed 8 steps test be codified as a standard pipeline contract?
  • If named layout artifacts are introduced, will future interpretation_artifacts also be put in hierarchical_result.json, or made into separate artifacts? layouts are natural within the result JSON, but boundary / bridge reasons tend to bloat.
