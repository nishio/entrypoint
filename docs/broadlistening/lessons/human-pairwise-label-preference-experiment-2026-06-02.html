Human Pairwise Preference for Label Quality

Translated from the Japanese original: wiki/analyses/human-pairwise-label-preference-experiment-2026-06-02.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: In label quality experiments, rather than having humans critique single labels, multiple label candidates generated from the same tree/evidence are compared in a blind A/B test that hides algorithm origins. The difficult full UI evaluation is decomposed into single labels, adjacent label sets, and labels with representative examples, and their pairwise preferences are used as judge calibration data.

Conclusions

Human evaluation for label quality experiments should not start with critiquing a single label. First, create multiple label candidates from the same tree/evidence/presentation context, and ask humans which is better, A or B. The role of humans is not to be a detailed rubric judge, but to return preferences from comparable candidates. From nishio-human-pairwise-label-preference-before-judge-2026-06-02

At this time, humans are not shown which algorithm/process A/B originated from. If names like current main, setwise, LLM grouping, or hierarchical are visible, humans are likely to choose based on preconceptions rather than actual label quality. The display order of A/B is also randomized/counterbalanced, and position bias is recorded. From nishio-blind-human-label-presentation-context-2026-06-02

This also changes the goal of judge improvement. The first judge v1 does not look at "can it verbalize the shortcomings of a single label," but rather "can it reproduce human pairwise preferences."

Why A/B First

When looking at a single label, humans cannot always immediately verbalize that "coverage is weak," "sibling distinction is weak," or "there is an unsupported axis." However, if two labels for the same cluster are placed side-by-side, it becomes easier to judge things like "this one is closer to the contents," "this one is confusing with its neighbors," or "it is short but missing information."

Therefore, human observation is not initially recorded as free-text critiques, but saved as preference records like the following.

{
  "preference_id": "pref-001",
  "comparison_id": "cmp-hierarchical-8-40-label-process-001",
  "tree_run_id": "hierarchical_8_40",
  "cluster_id": "level1:3",
  "candidate_a_labelling_run_id": "baseline_merge",
  "candidate_b_labelling_run_id": "sibling_aware_setwise",
  "algorithm_origin_visible": false,
  "candidate_a_display_position": "left",
  "candidate_b_display_position": "right",
  "presentation_context": "label_with_representatives",
  "ui_surface": "cluster_detail_panel",
  "factor_under_test": "labelling_process",
  "fixed_inputs": ["dataset", "extracted_arguments", "embeddings", "tree_run", "evidence_policy"],
  "winner": "b",
  "confidence": 2,
  "reason_tags": ["covers_more", "distinguishes_siblings"],
  "free_text": null
}

Free text is made optional. What is mandatorily required of humans is A / B / tie / unsure, a light confidence rating, and reason tags if needed.

Presentation Context

What is shown to the human together is also recorded as part of the preference. Since labels do not always exist alone in the actual UI, without separating the presentation context, it is unclear in which situation a label is good. From nishio-blind-human-label-presentation-context-2026-06-02

presentation_context What is shown What is mainly understood
label_only Only label text Whether it stands alone as a heading, whether it reads shortly
sibling_label_set A complete set of adjacent/sibling labels of the same parent Whether it can be distinguished from neighbors, whether it is readable as a label set
label_with_representatives Label + representative arguments Whether the label is supported by actual examples, whether it is missing important axes

Experiments that change presentation_context and experiments that change labelling_process are separated. When comparing algorithms/labelling processes, the presentation context is fixed. Conversely, when comparing presentation contexts, candidate labels are fixed and only the display context is changed.

full_ui_context is not used as the presentation context for the first clean A/B experiments. In the actual UI, cluster size, descriptions, representative examples, adjacent labels, hierarchy, layout, interaction, etc., all have an effect simultaneously, making it difficult to interpret what drove the preference. That is exactly why it is decomposed into three: label_only, sibling_label_set, and label_with_representatives. Full UI is treated as an integration check after narrowing down candidates with decomposition tests. From nishio-blind-human-label-presentation-context-2026-06-02

Relationship with the One-Factor Principle

"Creating multiple labels with different parameters" and "changing one factor at a time" do not contradict. In a single comparison block, the axis to be changed is narrowed down to one.

  • Labelling process comparison: Fix tree, evidence, and model, and make multiple candidates only for prompt/process.
  • Evidence policy comparison: Fix tree, prompt, and model, and make multiple candidates only for the materials shown.
  • Tree comparison: Fix labelling process, evidence, and model, and make multiple candidates only for tree generation.
  • Presentation context comparison: Fix candidate labels and tree, and change only label_only / sibling_label_set / label_with_representatives.

If multiple axes are mixed in the same A/B test, even if a human chooses B, it is unknown whether the prompt had an effect or the evidence had an effect. From one-factor-experiment-principle-2026-06-02

First Experiments to Run

The first experiment will not be a judge rubric but an A/B preference collection of label variants.

Things to fix:

  • Dataset: LLM grouping 400 items corpus
  • Tree: hierarchical_8_40
  • Evidence policy: Existing evidence or same representative artifact for now
  • Model: Same model
  • Display context: How to show cluster size, sibling labels, and representative arguments
  • Blind conditions: Algorithm/process names are hidden from humans. The display position of A/B is randomized/counterbalanced.

Things to change:

  • Labelling process/prompt only

What to ask humans:

  • Which is better, A or B
  • Whether tie/unsure
  • Whether confidence is low/medium/high
  • If choosing reason tags, around covers_more, distinguishes_siblings, more_concise, less_unsupported, better_heading

It is realistic to start with sibling_label_set or label_with_representatives at first. label_only is good for diagnostics looking at readability as a heading. Confirmation in full UI is not done as a clean A/B experiment, but after narrowing down candidates with these decomposition tests.

After this preference dataset is created, the same A/B is shown to the judge. The judge's evaluation is seen by how much it can reproduce human winner/tie/reason_tags.

Correcting Experiment Order

The corrected order is as follows.

  1. Create a comparison corpus that accumulates tree/labelling runs.
  2. Create label variants with different parameters under the same tree/evidence.
  3. Hide algorithm/process origins, fix presentation context, and ask humans for blind A/B preferences.
  4. Calibrate the judge to reproduce those preferences.
  5. Once the judge matches to a certain degree, use it to assist in evaluating broader parameter sweeps or view prototypes.

With this, excessive verbalization is not demanded of humans, and the judge can be nurtured in connection with human judgment.

Open Questions

  • Whether to start A/B on a per-cluster label basis or across an entire same top-level label set.
  • Whether sibling_label_set or label_with_representatives is better for the first presentation context.
  • After which decomposition test the full UI integration check should be performed.
  • Whether to make reason tags mandatory from the start, or start with only winner/tie.
  • How many pairwise preferences are needed to call it a judge v1 calibration.
  • When there are multiple human evaluators, whether to treat disagreements as label ambiguity or as rubric insufficiency.
