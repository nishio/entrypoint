Analysis Stance

Translated from the Japanese original: wiki/concepts/analysis-stance.md (commit 3459fc6).
Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: Kouchou-AI (広聴AI) is a tool built on the "structure grasping stance" (構造把握スタンス), not the "quantitative analysis stance" (定量分析スタンス). Its purpose is not to pretend to understand the whole by looking at cluster sizes and frequency distributions (falling into quantitative analysis), but rather to have the user read the overall structure. The single "grasping overall trends use-case" (全体傾向把握ユースケース = rephrased by tokoroten as "finding huge oversights / huge feelings of wrongness") handled by the Web UI is also realized through the structure grasping stance.

This page clarifies the core stance that permeates the design decisions of the Kouchou-AI (広聴AI) core. It was finalized when nishio organized the thought that Kouchou-AI is not a tool for quantitative analysis in a dialogue on 2026-05-30. From now on, design decisions should be narrowed down starting from this stance.

Two Design Stances

Quantitative Analysis Stance (Design completed with frequency distribution)

The way of thinking that "grasping the whole = measuring what is frequent and what is rare".

  • The output is completed with cluster + label + size.
  • Relationships between clusters (conflict / complement / causality) are not included in the main artifact.
  • Spatial visualizations like scatter plots are decorative. The main body is the list of frequency distributions.
  • The user looks at the aggregated results. They have no responsibility to read the structure.

There are tools that adopt this stance, and there are use cases where it is sufficient. However, Kouchou-AI does not take this stance.

Structure Grasping Stance (Design that makes the user read the structure)

The way of thinking that "grasping the whole = the accumulation of individual opinions ≠ the whole picture. Grasping the whole comes only after reading the structure".

  • The output is not a mere frequency distribution, but an apparatus for the user to decipher the structure.
  • Scatter plots / cluster layouts / hierarchical tree / drill-down are means to make the user read the structure.
  • It does not go as far as explicitly extracting and drawing the structure as an artifact. The user reads it.
  • Grasping the overall trends is not about counting numbers, but grasping the contours of the issue space.

Kouchou-AI = Structure Grasping Stance

The Kouchou-AI core is designed with the structure grasping stance.

We set the "grasping overall trends use-case" (label-quality-redesign-reset-2026-05-30) as the only use-case contract handled by the Web UI / standard run, but this does not mean creating a quantitative analysis-like apparatus to "look at the frequency of the top N topics". It is a premise that the grasping overall trends use-case is also realized through the structure grasping stance.

As an operational rephrasing by tokoroten, the grasping overall trends use-case can be expressed as an apparatus to "find huge oversights, huge feelings of wrongness". It is more specific than "grasping overall trends" and easier to use as a criterion for judging what to show and what not to show. From slack-stance-discussion-2026-05-30.

Specifically, the means by which Kouchou-AI realizes the structure grasping stance:

  • Scatter plot (current main figure): An apparatus to directly make the user read the layout of the opinion space.
  • Cluster + label + drill-down (current state): Returning to the original text starting from the cluster and making the user read the structure.
  • Hierarchical tree: Showing the hierarchical structure from coarse to fine.
  • semantic island map prototype (semantic-island-map-prototype-2026-05-26): A main figure candidate under consideration that divides between clusters and within clusters to make the user read the structure.

These do not "extract the structure as an artifact". They implement the structure grasping stance as an apparatus to make the user read the structure.

The meaning of "not a quantitative analysis tool"

This phrase does not say "do not count numbers". It says "do not pretend to understand just by counting numbers".

Implications:

  • It does not promote as a product the simplistic reading that "it is important because the cluster size is large".
  • It does not lean towards a UI design completed with a list of labels + sizes (= avoids falling into quantitative analysis).
  • However, the size and cluster ID are output secondarily. It's not "not counting", but "not only counting".

The reader is not "someone who reads" but "someone who explains"

As an evaluation axis for the structure grasping stance, not only "can the reader read the structure?" but also "can the reader explain the structure to others / can they talk while pointing at it?" is added. The reader is not someone who consumes passively, but a subject where policymakers / local governments / citizens (re)narrate the structure towards others. If the report cannot provide material to say "let's talk about this", it will be shelved by the reader.

As a typical example of this "someone who explains", there is the internal demo role (bridge role). They are the ones who show the working report to decision-makers / budget deciders, and they themselves are often neither engineers nor data scientists. The actual spread of Kouchou-AI is carried by this layer, so whether the evaluation axis of structure grasping (nature as explanation material / nature as cross-referencing material) is satisfied is particularly questioned by this reader. See also the "3 reader personas" in broadlistening-tool-ecosystem-vision.

Verbalizing one source of ease of talking, it is "surprise = discovery of a discrepancy with the classification the reader implicitly held beforehand". The reader visits with their own mental model (agree/disagree, cost/effect, etc.), and when the difference between that and the current findings becomes visible, it becomes "ah, I can talk about this".

However, since "what one finds surprising" depends on individual subjectivity, we do not adopt a design that guarantees surprise itself as a product. What can be aimed for as a product is one step before that: providing "material that is easy for the reader to cross-reference with their own prior mental model".

  • ❌ An apparatus to generate surprise (subjectivity-dependent and cannot be guaranteed)
  • ✅ An apparatus to provide cross-referencing material (subjectivity is placed on the reader's side)

Scatter plots are strong in this sense: it is easy for the reader side to superimpose "if I color-coded it in my mind", "what would I name it under my classification", and "how would I cut it at my granularity". On the other hand, a list of cluster + label + size (the imagined form of falling into quantitative analysis) is difficult to cross-reference in this way. The design judgment of the structure grasping apparatus can use "ease of cross-referencing" as a yardstick.

Furthermore, "what makes a report strong as explanation material" and "the boundary for being shelved" depend on individual subjectivity, so it is an area handled by separate tools or operations / literacy, not product features.

Structural limits of the structure grasping apparatus — the phenomenon of "stopping"

Observation by ohki-shingo: "Looking at the report generated by Kouchou-AI, being unable to find insights, going 'hmm', and stopping there." This can be explained as a structural consequence of the structure grasping apparatus. When the reader side does not have a prior mental model, or when the prior model matches the current findings, even if there is cross-referencing material, "difference = surprise" is not born, and the motivation to explain does not arise. From slack-stance-discussion-2026-05-30.

Implications: Even if the structure grasping apparatus is polished, it will not reach readers who do not have a prior model. This is already team-aligned as a limit of the product (entrust to the ability / context of the reader side). An operation with an explicit prior model, such as "how opinions map or do not map against an already existing comprehensive plan" mentioned by ohki-shingo, is the scenario where the structure grasping apparatus shines the most.

UX guidelines for the Web UI

Readers of the Web UI often cannot distinguish what they want to do at a resolution like "grasping overall trends / grasping structure / detailed exploration". Therefore, a UI that makes them choose (what they want to do) does not function. Instead, we design with the following policies. From slack-stance-discussion-2026-05-30.

  • Provide a "finding huge oversights / huge feelings of wrongness" (= grasping overall trends use-case) view as the default mode.
  • Lean towards a post-induction type UX that guides to another view after seeing the reaction.
  • A mode switch at the level of "rough mode (fewer top clusters, suitable for scatter plots) / detailed mode (more clusters, suitable for tree views)" could be prepared.
  • However, forcing a choice creates a "which one should I choose?" problem, so assistance making them comparable via a sample analysis results catalog is needed.
  • User custom prompts and complex analysis method selection are on the CLI side (broadlistening-tool-ecosystem-vision).

Ecosystem — CLI and shared community

The basic policy of delegating artifact extraction features (KJ method (KJ法) 6 principles #3 #4 #5 series) and minority opinion rescue systems to separate tools while maintaining the structure grasping stance (label-quality-redesign-reset-2026-05-30) is specifically implemented in the form of stacking diverse experimental features in the CLI and encouraging trial and error and sharing within the community. For details, see broadlistening-tool-ecosystem-vision.

Division of labor between structure grasping stance and "complementing with separate tools"

Among the 6 KJ Method-like principles (kj-method-broadlistening-framing-2026-05-25), #3 (human scrutiny of nameplates) / #4 (minority survival) / #5 (showing structure = conflict/causality) became a policy of not including them in the Kouchou-AI core, but complementing them with a group of separate tools in the future in the dialogue on 2026-05-30. This does not contradict the adoption of the structure grasping stance.

Organization:

  • Kouchou-AI core = An apparatus that maintains the structure grasping stance. It has UI / visualization / drill-down to make the user read the structure.
  • Separate tools = Apparatuses that extract specific artifacts within the structure grasping stance. Conflict cards, causality illustration, human scrutiny of nameplates, minority residual extraction, etc.
  • Both share the "structure grasping stance" while delegating responsibilities.

In other words, adopting the structure grasping stance does not mean "Kouchou-AI does everything". It is an ecosystem design where Kouchou-AI is the entrance for structure grasping, and the group of artifact extraction tools is the exit for structure grasping.

Derived design decisions

With the determination of the structure grasping stance, the following decisions are automatically directed.

  • Maintaining the scatter plot (open-decisions A1): Since the scatter plot is a major apparatus of the structure grasping stance, it is preserved until a better candidate is found. Alternative candidates are evaluated as structure grasping.
  • Positioning of semantic island map prototype: It has the possibility of entering the Kouchou-AI core as a main figure candidate for structure grasping. It did not "fall into a separate tool candidate".
  • Whether to cut the interpretation_artifacts step (pipeline-step-addition-framing-2026-05-27 / thinking-targets 3-1): It is a structure grasping stance, but since artifact extraction is on the separate tools side, it leans towards the direction of not putting it in the Kouchou-AI core.
  • Continuous engagement (thinking-targets 1 series #6): It aligns as a design that extends the apparatus to "make the user read the structure" along the time axis. Support for continuing to read the structure continuously is an extension of structure grasping.
  • 7 requirements for public UI (public-ui-requirements-for-broadlistening): ohki-shingo's organization leans towards structure grasping. With the stance determined, its consistency as an upper contract on the public UI side has increased.

Open Questions

  • Whether the scatter plot or the semantic island map is a better approach as the main figure for structure grasping is waiting for the prototype evaluation results. The judgment criterion is "how well the user could read the structure" (any operationalization is pending).
  • To what extent to support "making the user read the structure" as a product (e.g., whether to include an onboarding tutorial for reading the structure, whether to provide hints for untrained users) is undecided.
  • How to visually prevent "not only counting" on the Web UI is undecided (displaying the cluster size large might induce falling into quantitative analysis).
  • Where the group of separate tools should exist within the ecosystem is unorganized (in-house / OSS / individual development).
