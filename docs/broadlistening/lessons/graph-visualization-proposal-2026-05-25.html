Drawing an Opinion Map as a Graph: Intra-Cluster Minimum Spanning Trees and Inter-Cluster Bridges

Translated from the Japanese original: wiki/analyses/graph-visualization-proposal-2026-05-25.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: A proposal to break away from the design of burdening UMAP 2D with both semantic clustering and visualization quality, and instead visualize as a graph drawing using intra-cluster MST + mutual kNN, inter-cluster bridge edge, and 2-stage cluster-separated layout. This can be an answer from the visualization side to the existing niizuma critique.

gpt-mst-bridge-visualization-brainstorm-2026-05-25 is a proposal that improves upon nishio's visualization idea of "adding intra-cluster MST + cross-cluster edges within the range of not breaking clear separation" by comparing it with existing research.
The value of this proposal lies in replacing the discussion around UMAP 2D with a graph drawing design problem, rather than UMAP parameter tuning or clustering algorithm selection.

This idea was also shared in #2_開発_広聴ai_アルゴリズム開発 on 2026-05-25 as the point cloud requirement of "1 opinion = 1 point", the collision between UMAP 2D and semantic clustering, and the combination of intra-cluster MST and inter-cluster bridge edges. From weekly-log-2026-05-20.

1. Rereading the problem of UMAP 2D as a collision of 3 requirements

Rereading the issues exposed by niizuma-thread-algorithm-critique from the visualization side, UMAP 2D is trying to satisfy 3 requirements simultaneously:

  • Want to see it as a point cloud (1 opinion = 1 point)
  • Want it to be semantically grouped (semantic clusters are correct)
  • Easy to see and understand (clusters appear separated)

These do not hold concurrently. Semantically correct clusters create enclaves and overlaps in 2D, and easy-to-see separation breaks semantic fidelity. From gpt-mst-bridge-visualization-brainstorm-2026-05-25.

The solution in UMAP 2D is to let the meaning be read by position. The solution in MST + bridge edge is to let the semantic relationship be read by edges. The latter can compensate for the distortion of 2D coordinates with a separate channel called edges, so the collision can be dispersed.

2. Can be an answer from the visualization side to the niizuma critique

niizuma-thread-algorithm-critique ultimately organized that the artifacts returned by Kouchou-AI (広聴AI) should be divided into 3 types:

  • Analysis artifact (which opinion belongs to which issue group)
  • Display artifact (UI for non-experts to grasp the overall picture and trace to individual opinions)
  • Explanation artifact (material to explain "why it was divided that way" in press, municipalities, and external reviews)

The MST + bridge edge proposal separates these into different channels within the same diagram:

Role Channel
Analysis artifact cluster assignment (color + cluster outline / hull)
Display artifact point placement + intra-cluster MST / kNN (position and backbone)
Explanation artifact inter-cluster bridge edge + relation type + reason

In particular, the relation type (same claim / adjacent issue / cause-effect / contrast / boundary) and reason of the bridge edge directly function as an explanation artifact. This is a component that was missing in the UMAP 2D scatter plot.

3. A different direction from tokoroten's TTTC reading

In tokoroten-spectral-clustering-reading, TTTC-like spectral clustering was understood as cleaning up the 2D geometry created by UMAP. tokoroten's reading is a direction to find a more natural way of cutting than k-means while leaving the scatter UX.

In contrast, this proposal is a direction to recreate the 2D geometry itself with graph drawing, and does not depend on UMAP.

Approach Starting point of 2D geometry Where semantic clustering resides
Current Kouchou-AI (広聴AI) UMAP 2D KMeans after UMAP
TTTC UMAP 2D (small n_neighbors) SpectralClustering after UMAP
TMAP / This proposal graph layout (MST + kNN + cluster separation) graph construction from embedding / LLM affinity

In other words, there is a theoretically valid option in research not only to "change UMAP -> k-means to spectral", but also "not to use UMAP". From clustering-deep-research-findings-2026-05-25.

4. Validity of 2-stage layout

The 2-stage design proposed by GPT and modified after nishio's pointing out ("if bridge is display-only, cluster placement becomes arbitrary"):

  1. Inter-cluster layout — Place each cluster as a meta-node. Inter-cluster weight is an aggregated value such as top-3 mean.
  2. Intra-cluster layout — Place points with MST + mutual kNN. Fit them around the cluster center.
  3. Draw bridge edge — Plays 2 roles: drawing lines between points i, j + weak layout constraints between cluster centers.

This is a method consistent with the weighted edge design of clustered graph drawing (Frishman et al.) and stress majorization (Gansner et al.), and is not something invented from scratch.
The essence hit by nishio's modification is that "making bridge overlay-only" breaks the layout, which is a design point already explicitly handled in graph drawing research.

5. Overall MST should be avoided

In nishio's original idea, it was "extract N:N similarity relationships with LLM and connect them from the strongest relationships to make a spanning tree", but if it is an overall MST, all opinions will always be connected into a single tree, so a connection is created somewhere even between originally distant clusters, making it look like an "important bridge". From gpt-mst-bridge-visualization-brainstorm-2026-05-25.

Instead, it is safer to divide it into "intra-cluster MST + a few inter-cluster bridges". This can be read as a configuration adding semantic bridge edges to a MapSets-like idea (connecting points of the same cluster with a spanning tree to create non-overlapping regions).

6. Portability to current kouchou-ai

The current kouchou-ai has a Plotly scatter plot + hierarchical tree UI. Three ways are conceivable to introduce the MST + bridge type layout:

  • A. Maintain the existing scatter plot, and add only the bridge edge as an overlay — Can be implemented with minimal changes. However, since the scatter coordinates remain UMAP 2D, only half of the advantages of this proposal (recreating the layout) can be obtained.
  • B. Add cluster-separated graph layout to another view as a View plugin — A choice at the viewer level, not analysis_mode. The user switches between "scatter view" and "graph view". Consistent with the view plugin contract of public-ui-requirements-for-broadlistening.
  • C. Add MST edges / bridge edges / cluster centers to the output schema of analysis-core — Full path. A design where the new viewer uses this while maintaining backward compatibility.

In the short term A, in the medium term B, and in the long term C seem to be the logical thread. The framework of analysis_capabilities / viewer requirements shown in llm-grouping-implementation-plan can also be used here.

7. Evaluation axis: placing bridge usefulness at the center

gpt-mst-bridge-visualization-brainstorm-2026-05-25 places bridge usefulness at the center as the evaluation axis of this proposal:

Evaluation What to look at
semantic coherence Whether intra-cluster opinions can be read with the same heading
visual separation Whether clusters are visually separated
bridge usefulness Whether inter-cluster edges are insightful
stability Whether it does not change significantly by re-executing LLM or changing the order
editability Whether it is easy for humans to merge / split / delete edges

bridge usefulness is an indicator that has not appeared in conventional UMAP evaluations, and is the core value of this proposal.
This is also consistent with the principle of "not collapsing the evaluation axes into one" of clustering-deep-research-findings-2026-05-25.

8. Handling as a design decision

Whether to put this proposal on the implementation backlog of the current kouchou-ai is another matter.
development-priority-roadmap-2026-05-23 / strategic-development-order-2026-05-23 prioritize Windows distribution, known bugs, and operation infrastructure, and the recreation of the visualization design is a lower priority than those.
However, there is high value in keeping this proposal as an alternative when the limitations of scatter compatibility are exposed in small-scale demonstration experiments like llm-grouping-experiment.

Organization of priorities:

  1. Discussion stock — Keep this proposal as a "usable card". The preliminary stage before dropping it directly into code.
  2. Small-scale demonstration — It is worth prototyping MST + bridge once in small-scale UI experiments of the policy-pr-hub.vercel.app family.
  3. schema extension — The direction to put MST / bridge in the output of analysis-core is suspended because there is no reason to hurry.

Open Questions

  • Can the MST + bridge design be the same for less than 100 cases and over 10,000 cases? When N is large, MST + kNN is challenged by scalability in both drawing and calculation. Hierarchization (cluster-of-clusters) may be necessary.
  • At which LLM model generation will the automatic classification accuracy of bridge edge relation type be put to practical use? Misclassified bridges have a high risk of misguidance, and the impact of misjudgment becomes a design weakness that dominates the appearance.
  • The λ_inter greedy schedule of the 2-stage layout has a different optimal value for each dataset. Research to empirically determine the default value is necessary.
  • When implementing this proposal as a view plugin, should it co-exist with the existing Plotly scatter plot or replace it? If co-exist, UI duplication increases, and if replace, it betrays the expectations of existing users.
