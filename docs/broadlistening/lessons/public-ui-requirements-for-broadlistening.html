What Is Required of a Public UI for Broad Listening Results Is Not "Whether It Is a Scatter Plot"

Translated from the Japanese original: wiki/analyses/public-ui-requirements-for-broadlistening.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: The requirements for the public UI of broadlistening results are not "whether it is a scatter plot", but the volume, perspectives, issues, traceability to individual opinions, avoidance of burying minority opinions, elimination of arbitrariness, and visualization of the next questions. Derived from ohki-shingo's organization.

llm-grouping-background-history organized the "tension between the analysis style not assuming embedding and the scatter plot-centric product" chronologically, but the remaining question there, "how to replace the role played by the scatter plot with another view", remained conceptual.
In slack-public-ui-requirements-2026-05-23 on 2026-05-23, ohki-shingo explicitly broke down this question and verbalized the requirements for the public UI into 7 items. This page records this organization in connection with the design decision to make analysis_mode / view independent.

Conclusion

The requirements for the public UI of broadlistening results can be organized into the following 7 items. This is independent of embedding / scatter plots, and is a view-side contract that should be satisfied by any analysis method: long-context LLM direct classification / taxonomy-guided / metric space-based.

  1. Visualization of volume — What kind of voices and how many were handled
  2. Visualization of perspectives for organization — From what perspectives they were organized
  3. Visualization of major issues — What the major issues are
  4. Traceability to individual opinions — Whether it can be traced back to the original individual opinions
  5. Avoidance of burying minority opinions — Whether minority opinions or voices difficult to classify are not buried
  6. Elimination of arbitrariness — Whether it does not look like the administration arbitrarily summarized them
  7. Visualization of the next questions — Whether what should be discussed or explored next is visible

From slack-public-ui-requirements-2026-05-23

Why the current scatter plot is accepted

ohki-shingo organizes that the scatter plot itself is not the essence. It is accepted because it is easy to simultaneously present the following 5 elements on a single screen:

  • It can be seen at a glance that a large amount of opinions are handled (→ Requirement 1)
  • It looks like they are organized by similar opinions (→ Implicit presentation of Requirement 2)
  • The whole picture can be explored (→ Requirement 3)
  • It can return not only to summaries and labels, but also to individual opinions (→ Requirement 4)
  • It looks like the administration did not arbitrarily summarize them, but published them with transparency (→ Requirement 6)

In other words, it can be read that the value of the scatter plot is not the precision of distance, but the simultaneous presentation of these requirements. From slack-public-ui-requirements-2026-05-23

The discussion on the "limits of the scatter plot method" traced by llm-grouping-background-history was centered on the limits on the analysis side, such as clustering accuracy, burying of conflicting axes, and adverse effects of dimensionality reduction, but the organization on this page isolates the role of the view side. The two are in a complementary relationship.

Non-essentiality of embedding distance precision

Using the requirements in reverse, the upper limit of the distance precision required for the view side can be seen.

  • Separation between clusters is visible: Required (→ Requirements 2, 3, 5)
  • Distance precision within clusters: Not required (Sufficient if they are displayed naturally close)

From slack-public-ui-requirements-2026-05-23

This is consistent with the judgment of slack-design-intents-2026-q1 in 2026-Q1 recorded by llm-grouping-background-history, that "embedding is not theoretically essential, but is a convenient scaffold for transition". For the x/y calculation to project LLM grouping-based analysis into scatter plot compatibility, it means that it is not necessary to reproduce the semantic distance with high precision, as long as the cluster grouping is visually preserved.

This greatly relaxes the technical bar for the short-term scatter plot compatibility plan (x/y compatibility of analysis_mode=llm_grouping in the PR #827 plan of pipeline). Force-directed placement, per-cluster local UMAP, 2D placement based on LLM labels, etc., all enter as candidates that "satisfy sufficient distance precision as a public UI".

Correspondence with independent analysis_mode / view

In slack-design-intents-2026-q1 and llm-grouping-background-history, visualization separation has been explained as:

  • "A necessary condition to accept LLM grouping-based analysis into the platform" (discussion of necessity)

The 7 items on this page supplement this with "sufficient conditions on the view side".

In other words, when designing the analysis_capabilities / requirements of plugin-system, the contract for the view plugin can be considered in the following 2 layers:

  1. Lower contract (existing) — Input data structure (cluster tree / presence of embedding / individual argument list, etc.) and machine-readable capability
  2. Upper contract (this page) — Satisfying the 7 requirements as a public UI

With only the lower contract, "a view that is scatter plot compatible but cannot return to individual opinions" or "a view that visualizes clusters but buries minority opinions" would pass as a plugin. If the upper contract is explicitly stated in the docs / design review side, it is easier to judge the addition or replacement of a view plugin based on "whether it can maintain its role as a public UI".

Matching with structure grasping stance / overall trend grasping use case / division of labor with other tools (Added 2026-05-30)

Overlaying the organization of analysis-stance and label-quality-redesign-reset-2026-05-30 finalized on 2026-05-30 (structure grasping stance, single overall trend grasping use case, KJ principles (KJ原則) #3/#4/#5 complemented by other tools) onto the 7 requirements, the responsibilities are divided as follows.

# Requirement Responsibility
1 Visualization of volume Kouchou-AI (広聴AI) main body
2 Visualization of perspectives for organization Kouchou-AI main body (to be read as a structure grasping device)
3 Visualization of major issues Kouchou-AI main body (to be read as a structure grasping device)
4 Traceability to individual opinions Kouchou-AI main body
5 Avoidance of burying minority opinions Other tools. The overall trend grasping use case leans towards exhaustive partitioning and is determined not to create a minority residual artifact (label-quality-redesign-reset-2026-05-30), so the Kouchou-AI main body does not bear it.
6 Elimination of arbitrariness Kouchou-AI main body
7 Visualization of the next questions Other tools. The interpretation_artifacts area, such as boundaries / counterexamples / bridges / unresolved cards, is on the other tools side (pipeline-step-addition-framing-2026-05-27).

In other words, the Kouchou-AI main body bears 5 of the 7 requirements (1/2/3/4/6). The remaining 2 (5/7) are expected to be borne by other tool groups in the ecosystem, and are not permanently incorporated into the main body.

In addition to this, 2 items are added as evaluation axes for the structure grasping device (From analysis-stance):

  • Is it material that the reader can explain to others? (reader = not a passive reader, but a narrator who explains the structure to others)
  • Is it material that is easy to cross-reference with the reader's prior mental model? (Surprise itself is subjective and outside the scope of the product; the materiality for cross-referencing is the subject of product design)

The 7 requirements remain valuable as ohki-shingo's organization, but as a view design decision for the Kouchou-AI main body, it is more realistic to evaluate with "5 items of the main body + 2 additional axes of structure grasping".

Implications for the existing scatter plot view

The scatter plot-centric view of the current apps/client-statics can also be evaluated with these 7 requirements:

Requirement Guarantee in the current scatter plot view
Visualization of volume ◯ (The sense of volume is visible by the total number of points)
Visualization of perspectives for organization △ (There are cluster labels, but the basis for the chosen perspective is weak)
Visualization of major issues △ (Cluster summaries are displayed, but they are not necessarily organized as "issues")
Traceability to individual opinions ◯ (Reach the original text by clicking a point. However, it was broken for a long time in #710 -> PR #857)
Avoidance of burying minority opinions × tendency (Easy to be crushed by dimensionality reduction) From llm-grouping-background-history
Elimination of arbitrariness ◯ (Arbitrariness appears weak because raw opinions and classifications are visible simultaneously)
Visualization of the next questions × (No explicit display of "issues to be discussed next")

The fact that the current view is "accepted as a total while including △ and ×" also means that it is established by a combination of strong and weak requirements. When creating a new view, if you lean towards improving the weak requirements (5, 7) while maintaining the strong requirements (4, 6), it is more likely to be evaluated as "better than a scatter plot" as a public UI.

Open Questions

  • Of the 7 requirements, #2 Visualization of perspectives for organization and #7 Visualization of the next questions seem stronger in LLM direct classification / taxonomy-guided analysis, but does this naturally emerge if ohki-shingo's organization is dropped into the implementation contract, or does it require separate design?
  • Organized as a self-answer in the context of use by municipalities, but are the 7 requirements the same in other contexts such as elections, citizen participation, and internal company surveys, or does the weight change for each context?
  • Assuming that a 2D placement that guarantees only cluster grouping is performed in the short-term scatter plot compatibility plan, how should the way it is decided for that placement be disclosed on the docs / reports to satisfy the "elimination of arbitrariness" requirement?
  • If the 7 requirements on this page are officially described in the docs as a contract for the view plugin, which page will be the original text (here, plugin-system, or broadlistening)?
