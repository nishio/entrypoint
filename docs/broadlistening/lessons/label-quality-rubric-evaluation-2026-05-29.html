Evaluating Label Quality with Binary Rubrics

Translated from the Japanese original: wiki/analyses/label-quality-rubric-evaluation-2026-05-29.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: It is better to decompose the judge of cluster label quality into a rubric evaluation of binary criteria + weights + fatal penalty, rather than an abstract 1-5 point scale. First, it should be calibrated against human judgment using the existing judge bundle of [8,40], and run as an experimental artifact instead of putting it into the standard pipeline.

The "label quality" handled here refers not to GitHub issue labels, but to the quality of the cluster label / description that appears in the analysis output of Kouchou-AI (広聴AI).

Conclusion: If we are to improve the current label judge, it is better to decompose it into binary criteria + points like the Ubie article style, rather than increasing abstract 1-5 point scoring. While keeping consistency / specificity / comprehensiveness / distinctiveness as upper categories, the actual judge should return true/false on whether it "meets the criterion". From zenn-llm-as-a-judge-rubric-evaluation-2026-05-29 and label-judge-mechanism-2026-05-25.

Why

The existing OpenAI judge has split winners between the cluster-level judge and the label-set direct judge, and since the generator and the judge are from the same lineage of LLMs, we need to suspect self-evaluation bias. From label-judge-mechanism-2026-05-25.

On the other hand, in human judgment, there is a product policy stating that "labels are summaries, not tables of contents", "prefer redundancy over omission", and "cover up to the top 2-3 axes". Therefore, the judge also needs to treat the omission of important axes closer to fatal, not just focus on "readable brevity". From label-coverage-policy-2026-05-29.

Also, in current main 0c294da, both hierarchical_initial_labelling and hierarchical_merge_labelling are defaulted to sampling_num=10, and label arguments within a cluster by randomly sampling them. In large clusters, label quality issues arise not only from the "judge" but also because they are "not visible in the input". From source-code.

Proposed Rubric Shape

Output the following JSONL with 1 row per 1 cluster. Be sure to save not only the total score but also the judgment for each criteria.

{
  "rubric_version": "label-quality-v0",
  "cluster_id": "cluster-level-1:5",
  "label": "AIによる顧客体験と業務効率の向上",
  "score": 48,
  "max_score": 75,
  "score_rate": 0.64,
  "fatal_flags": [
    "unsupported_axis"
  ],
  "criteria_results": [
    {
      "id": "COV_MAIN_TOPIC",
      "axis": "coverage",
      "points": 20,
      "criteria_met": true,
      "signed_score": 20,
      "rationale": "shown arguments contain business efficiency and data analysis"
    }
  ]
}

The scoring looks at fatal_flags as well as score_rate. For example, "the label claims an axis not in the material" breaks the UI trust even if the average score is high, so it is made a gate condition.

Cluster-Level Criteria v0

id points criterion
COV_MAIN_TOPIC +20 The label includes the most central argument among the presented arguments
COV_TOP_AXES +15 When the cluster contains multiple axes, the top 2-3 axes appear in the label or description
GROUND_LABEL +15 Each main word in the label is grounded by the presented arguments or child cluster label/description
DESC_BOUNDARY +10 The description explains "what is included" and supplements arguments that would be dropped by the label alone
DIST_SIBLING +10 Compared to the list of sibling labels, the coverage scope of this label is distinguishable
SCAN_LENGTH +5 The label fits within a scannable length in the UI, and differences are not hidden simply by using a generic prefix
REGISTER_OK +5 It is not an unnatural colloquialism or excessive marketing word in a public / policy context
UNSUPPORTED_AXIS -25 The label claims an important axis that cannot be confirmed from the presented material
MISSING_VISIBLE_AXIS -20 Although there is a clear important axis in the presented material, it is dropped from both the label and description
DUPLICATE_SIBLING -15 The meaning overlaps significantly with a sibling, making it difficult for the user to judge which one to open
GENERIC_BUCKET -10 Although there are specific arguments, it escapes into generic buckets such as "AI utilization" or "social issues"

In this v0, COV_TOP_AXES and MISSING_VISIBLE_AXIS are the parts where the judgment of "covering up to the top 2-3 axes" from label-coverage-policy-2026-05-29 has been dropped into the judge.

Label-Set Criteria v0

Apart from the cluster unit, the entire top-level label set is also evaluated once. This corresponds to the Label-Set Direct Judge in label-judge-mechanism-2026-05-25, but this is also divided into binary criteria.

id points criterion
SET_DISTINCT_HEADINGS +15 The main labels can be distinguished from each other even when just looking at the first few words
SET_GRANULARITY +10 The granularity does not deviate significantly between labels
SET_COVERAGE +15 The top-level label set roughly covers the main themes of the presented clusters
SET_NO_PREFIX_NOISE +5 Common prefixes like By AI technology... do not hinder the understanding of differences
SET_REGISTER_CONSISTENT +5 The tone is consistent across the entire label set
SET_DUPLICATE_PAIR -20 There is a label pair with almost the same meaning
SET_HIDDEN_RESIDUAL -15 Important themes of large clusters have become invisible on the label set

Input Design

The material passed to the judge is divided into 3 layers.

  1. label / description / size
  2. representative arguments
  3. sibling labels

However, since the labeling itself in current main relies on random 10 items, showing only the same 3 items to the judge is likely to cause misjudgment. First, we will calibrate with the existing label-refinement-judge-bundle-2026-05-25, and then see how the judge results change between the all-args input and sample input. From label-refinement-judge-bundle-2026-05-25 and source-code.

Experimental Plan

  1. Fix the v0 rubric: Fix the above criteria as JSON or YAML, and leave rubric_version in the evaluation results
  2. Re-evaluate with existing bundle: Evaluate none / setwise / contrast / balanced at both the cluster-level and label-set
  3. Match with human judgment: Treat "prefer redundancy over omission" and "top 2-3 axes" from label-coverage-policy-2026-05-29 as the product policy closer to the correct answer, and see if the rubric can detect the same failures
  4. Check judge reproducibility: Evaluate the same input 10-50 times and calculate the match rate for each criterion. Look at the match of criteria_met, not the average of the total score
  5. Input scope comparison: Under the 3 conditions of representative 3 items, random 10 items, and all args, observe the appearance of UNSUPPORTED_AXIS / MISSING_VISIBLE_AXIS
  6. Adoption judgment: Do not make it a standard pipeline step until human alignment is achieved, but save it as an experimental evaluation artifact

Implementation Notes

An offline script like scripts/evaluate_label_quality_rubric.py is a good implementation candidate before putting it into the standard pipeline. The inputs are hierarchical_merge_labels.csv and hierarchical_clusters.csv, and the outputs are label_quality_rubric.jsonl and label_quality_summary.csv. With this, it is easy to put it on the label quality improvement tracking of #881, and it can be compared without increasing the pipeline contract.

For criteria execution, in initial experiments, 1 cluster 1 call returns all criteria as JSON. 1 criterion 1 call like the Ubie article is strict for seeing reproducibility, but it is expensive from the start. First, find weaknesses with 1 cluster 1 call, and individually make calls only for criteria that vary. From zenn-llm-as-a-judge-rubric-evaluation-2026-05-29.

Do Not Optimize Only The Score

This rubric is not used to mechanically decide the winner of label refinement, but to decompose why it is bad and decide the next experiment. For example, if SCAN_LENGTH improves but MISSING_VISIBLE_AXIS worsens, it is not an improvement under the product policy. From label-coverage-policy-2026-05-29.

Open Questions

  • Can the judge stably recognize the "top 2-3 axes" of COV_TOP_AXES? If not, a preprocessing step to first extract topic candidates from the argument group is needed.
  • If the context is long with all-args input, will judge oversights increase? Long text input increases coverage, but can cause distraction on the judge side.
  • To what extent should fatal_flags be a product gate? Even if it can be gated in experiments, differences in label preferences and usage will appear in user data.
  • How many human judges are sufficient? First, it is realistic to start with the top-level 8 clusters of [8,40].
