The Essence of the Default Cluster Count Problem

Translated from the Japanese original: wiki/analyses/auto-cluster-defaults.md (commit 3459fc6). Machine-translated by Gemini and not yet reviewed by NISHIO Hirokazu.

Summary: The essence of the cluster count default issue is not about "algorithm selection" but rather "the discrepancy in AI usage paths between docs, implementation, and interfaces," and PR #832 is a fix that narrows this gap.

It is closer to the reality to read the [3, 6] issue not just as a pure algorithm theory of "what is the appropriate number of clusters," but as a problem of which specific example written where propagates as the de facto default to AI and users. From issue-830-pr-832-auto-cluster-defaults-2026-05-18

1. The problem was that a bad example in the docs was directly tied to the CLI implementation

If [3, 6] had been just one example in the docs, it might have been solved by "fixing the example." However, in reality, compat / specs / plugin fallback also had [3, 6], and the analysis-core initialization path itself supplemented a fixed value.
Therefore, it is better to understand this problem not as "the explanation is outdated," but that the explanation, the implementation, and the AI's reference destinations were all biased in the same direction. From source-code

2. Admin already had a different common sense, creating a double standard within the repo

README / getting-started / Admin UI docs had another common sense of "1000 -> 10,100 based on the cube root," and users of the Web path read that. On the other hand, CLI / analysis-core users see the quickstart and fallback of [3, 6].
In other words, a double standard of "cube-root rule for Web" and "[3, 6] for CLI" had long coexisted within the repo. The meeting minutes from this time captured the exact moment this divergence was exposed by AI usage. From issue-830-pr-832-auto-cluster-defaults-2026-05-18

3. The value of PR #832 lies not in "optimization" but in "connecting existing tacit knowledge to the CLI"

The merged PR #832 did not revive advanced automatic exploration. What it did was simply adopt the cube-root rule, which was already in the Admin-side docs / UI, as the default behavior for analysis-core when omitted, and removed the fixed fallback.
However, this "simply" is important; unless explicitly specified by the user, the same lineage of common sense as the Web is now adopted in the CLI as well. This is less an algorithm improvement and more a restoration of consistency in usage paths. From issue-830-pr-832-auto-cluster-defaults-2026-05-18

4. The aim of the calculation is to "align the number of sub-elements per cluster at each stage while gently reflecting the increase in the number of items"

The formula itself is quite simple:

  • First layer: round(cuberoot(n))
  • Second layer: lv1^2

Since it uses a cube root, the number of items needs to increase by 8 times for the first layer to roughly double. In other words, the rule is oriented to not sharply increase the number of clusters even if the number of data items increases, maintaining the visibility of the top-level clusters first. From issue-830-pr-832-auto-cluster-defaults-2026-05-18

At the same time, this formula is not just "slow in its rate of increase," but makes it easy to roughly align the number of sub-elements hanging from one cluster at each stage.
If we view it as lv1 = n^(1/3) and lv2 = n^(2/3),

  • From the whole to the first layer, there are n / lv1 ≒ n^(2/3) items each
  • From the whole to the second layer, there are n / lv2 ≒ n^(1/3) items each
  • The number of second-layer clusters per one first-layer cluster is lv2 / lv1 = n^(1/3)

In short, it is an explicitly geometric-progression-like design that splits at roughly the same ratio each time you go down a hierarchy. It is easier to understand this not as an "optimal cluster count estimation," but as an operational rule to avoid making the branch structure extreme when put onto a 2-stage UI / report structure. From issue-830-pr-832-auto-cluster-defaults-2026-05-18

With this rule,

  • 125 -> [5, 25]
  • 1000 -> [10, 100]

come out exactly neatly. On the other hand, for 400, the implementation actually results in [7, 49], so the "7→50" in the README and others should be understood as an easy-to-read rounding for explanation purposes, and the numerical examples in the docs and the strict implementation values are not always 1:1. From issue-830-pr-832-auto-cluster-defaults-2026-05-18

5. Even so, a subtle shift from "comment count" to "argument count" has newly arisen

In the meeting minutes, it was initially discussed as "calculated from the number of comments," but with the materialization of Issue #830, the criterion became the number of arguments after extraction. This is natural as an implementation, allowing it to match the number of the clustering targets themselves.
On the other hand, the README / getting-started / how-to-use still explain it as "based on comment count," so it is currently in a state where the words in the Web docs and the implementation intent of analysis-core are slightly misaligned. From issue-830-pr-832-auto-cluster-defaults-2026-05-18

6. This case is also a lesson to consider that "docs read by AI are the implementation itself"

The reason the problem became visible in the 2026-05-18 meeting minutes was not because humans referred to the docs, but because the AI coding agent straightforwardly repurposed the [3, 6] from the quickstart.
In this sense, the docs for Kouchou-AI (広聴AI) are not just explanatory materials, but also reusable prompts / templates for AI. The lesson remains that specific examples should be evaluated not only on "whether the reader will copy and paste them," but also on "whether the AI will regard them as defaults." From meeting-minutes

7. In implementation reviews, it is necessary to check "whether it breaks with small inputs" to the end, rather than "whether the rule is elegant"

In the pre-merge review this time, a hole was found where 2 -> [2, 4] resulted in a crash due to n_clusters > n_samples. Even if the cube-root rule itself looks good, it was separately necessary to tighten the lower bound to ensure that the actual number of clusters passed to KMeans does not exceed the number of data items.
This point is important in software that is executed on small fixtures and test data, even while its main battleground is "hundreds to tens of thousands of items" like Kouchou-AI. As a general rule, in reviews of recommended value rules, it is safer to always look at the minimum cases (2, 3) as well as the large typical examples (1000 -> [10, 100]). From issue-830-pr-832-auto-cluster-defaults-2026-05-18

Open Questions

  • Should the Admin docs also be brought into line with the argument count base, or should the explanation based on comment count be kept for the Web UX?
  • After bringing the CLI / Web closer to the same rule, how should the room for returning to more advanced automatic selection like silhouette-score be preserved in the future?
